## How to use memory

**Label:** How to use memory

**Content:**
Your memory is a persistent graph. The better maintained, the more useful you are.

Core habits:
- Search before responding to anything factual, contextual, or personal
- Memorize immediately after learning something worth keeping
- Check `#prefixes` before labelling — right prefix = findable memory
- Link every new memory to what it relates to
- Never assume a memory's content from its label — always remember it fully before concluding
- Reconsolidate when understanding deepens or changes
- Review memories without associations periodically

One concept per memory, labelled precisely. A memory trying to capture everything captures nothing findable.

Your full guides live in associated memories. Search and read them — don't assume you know what they contain.

## When to memorize and recall

**Label:** When to memorize and recall

**Content:**
**Memorize when:** you learn something worth keeping. Do not wait. Good candidates: facts, definitions, decisions, reasoning behind decisions, contexts, rules, concepts, problems, corrected mistakes, lessons, assumptions, constraints, open questions, goals, opinions, things to avoid, patterns, insights, tradeoffs, warnings, status.

Check `#prefixes` before labelling. Check `Tutorials` for the right memorization approach.

Also capture context when it changes how the memory should be applied: "Context: learned while reading GRDB 6 docs during LocalMemoryGraph implementation". Only when genuinely useful.

After solving a problem or completing a task — ask: what did I just learn implicitly? Knowledge surfaced through doing is worth capturing too.

For long content — break into pieces. Each fact, insight, decision is its own memory. For full documents — use chunking. See "Memorizing documentation".

**Recall when:** before responding to anything factual or contextual. Before asking something the person may have already answered. At the start of a familiar topic.

**Associations:** How to use memory, How to label memories, How to associate, Recalling memories, Tutorials, #dont-forget

## How to label memories

**Label:** How to label memories

**Content:**
Format: `Prefix: keyword-dense specific phrase` — 3–8 words after prefix.

Rules:
- Always use a prefix — check `#prefixes` for the full list
- Front-load the most searchable word after the prefix
- No filler words
- Specific enough to distinguish — if two memories could share a label, split them

Bad: `"concurrency stuff"`, `"Fact: important thing"`
Good: `"Fact: GRDB requires macOS 12 minimum"`, `"Decision: chose mutual associations over directional"`

Cannot write a sharp label? The memory is too broad — split it.

Decision tree for prefix selection — search "Choosing a prefix" for the full guide.

**Associations:** How to use memory, When to memorize and recall, #prefixes, #dont-forget

## Choosing a prefix

**Label:** Choosing a prefix

**Content:**
Ask in order:

1. Person-related? → `Person:`, `Preference:`, `Opinion:`
2. Full document to preserve? → `Document:` — see "Memorizing documentation"
3. Research evidence or claim? → `Source:`, `Claim:`, `Evidence:`, `Finding:`, `Counterpoint:`, `Consensus:`, `Disputed:`, `Methodology:`
4. Evolving state? → `Goal:`, `Status:`, `Question:`
5. Decision? → `Decision:` for what, `Why:` for reasoning
6. Something that went wrong? → `Mistake:` for what, `Fix:` for correction
7. Conflict, stale data, or unverified fact? → `Warning:`
8. Constraint or rule? → `Constraint:` or `Rule:`
9. Fact or definition? → `Fact:` or `Definition:`
10. Otherwise → `Insight:`, `Lesson:`, `Pattern:`, `Warning:`, `Concept:`, `Assumption:`, `Tradeoff:`, `Alternative:`, `Avoid:`, `Context:`, `Example:`

No match? Check `#prefixes`. Still no match — create one and associate it to the relevant `#prefixes-*` category.

**Associations:** How to label memories, #prefixes, #dont-forget

## How to associate

**Label:** How to associate

**Content:**
Associations make memories findable by traversal, not just keyword. A memory with no associations is an island.

Associate: decisions to their reasoning, problems to solutions, concepts to definitions, rules to their context, lessons to situations, document chunks to their parent, any memory to relevant tag memories.

Associate at the moment of memorizing — this is when you have the most context. Always associate to relevant `#prefixes-*` tags.

Links are always mutual. Associate generously — an over-linked memory is still findable, an under-linked one is easily lost.

**Associations:** How to use memory, When to memorize and recall, How to label memories

## How to search effectively

**Label:** How to search effectively

**Content:**
Search before responding to anything factual, contextual, or personal.

Rules:
- Use specific keywords — "actor isolation" not "concurrency"
- Include the prefix in your keyword for precision — `"Decision: associations"` beats `"associations"`
- If first search fails, try different keywords or prefix before concluding you don't know
- Never conclude from a label — always remember relevant results fully before concluding

**Associations:** How to use memory, Recalling memories, Failed search recovery, #dont-forget

## Recalling memories

**Label:** Recalling memories

**Content:**
Three tools — use the right one:

- search — have keywords, not an ID. Start here.
- recall — have an ID. Returns label + associations only.
- remember fully — need actual content. Never skip this based on what the label implies — labels are short by design. Always read before concluding.

Flow: search → scan labels → recall for structure → remember fully when content needed.

Retrieve several related memories at once rather than one at a time.

## When to reconsolidate

**Label:** When to reconsolidate

**Content:**
Reconsolidation = replacing a memory with a sharper version. Refinement, not deletion.

Reconsolidate when: outdated, fragmented, too broad, poorly labelled, or understanding has deepened.

How: remember the old memory fully → memorize improved version with same associations → forget the old one.

Do not reconsolidate `#dont-forget` memories without being certain the replacement preserves everything important.

**Associations:** How to use memory, How to forget, Memory hygiene

## How to forget

**Label:** How to forget

**Content:**
Forget when: no longer true, fully absorbed into a better memory, or pure noise.

Do not forget when: still has value but needs updating (reconsolidate instead), tagged `#dont-forget` (pause and be certain), or you are unsure (leave it, review via memories without associations).

**Associations:** When to reconsolidate, Memory hygiene

## Memory hygiene

**Label:** Memory hygiene

**Content:**
Periodic maintenance. Do when conversation allows or at end of session.

- Review memories without associations — link, reconsolidate, or forget
- After major reconsolidation — check associations still make sense
- If search returns too much — some memories are too broad, split them
- If re-memorizing things already stored — labels are inconsistent, standardise
- Periodically check `#prefixes` is still complete

**Associations:** How to use memory, When to reconsolidate, How to forget, Finding memories without associations, Resolving conflicting memories, Handling corrections, What not to memorize, Time-sensitive memories

## Finding memories without associations

**Label:** Finding memories without associations

**Content:**
Memories without associations are not wrong, just disconnected.

For each: does it connect to something? Associate it. Still accurate? If not, reconsolidate or forget. Label good enough to find? If not, reconsolidate with a better label. Always remember it fully before deciding.

Many memories without associations = under-associating at memorization time.

## Memorizing documentation

**Label:** Memorizing documentation

**Content:**
Don't memorize the docs — memorize what is useful and non-obvious.

**Analytical:** extract constraints, non-obvious behaviours, recommended patterns, version-specific details, rules easy to forget.

**Chunking for full preservation:**
1. Parent: `Document: [name] — overview` — summary + associations to all chunks
2. Chunks use positional labels (not numbers):
   - `Document: [name] — beginning`
   - `Document: [name] — after [section]`
   - `Document: [name] — end`
3. Associate chunks to parent and to each other in sequence

Parent = index. Search finds it. Traversal surfaces chunks in order.

## Memorizing numbers and data

**Label:** Memorizing numbers and data

**Content:**
Quantitative facts need more care than qualitative ones — they go stale, lose context, and mislead when stripped of their frame.

Always capture alongside a number:
- **Source and date:** `"as of WWDC 2024"`, `"per the v6 changelog"`
- **Units:** never bare numbers — `"450ms"` not `"450"`
- **What it measures:** `"median cold start time on M1 Mac"` not `"startup time"`
- **Conditions:** sample size, environment, caveats

Label format: `Fact: [metric] — [system/context]`
Example: `"Fact: SQLite WAL mode write throughput — 2x baseline on iOS, per GRDB benchmarks 2023"`

Mark with `[expires: benchmark]` if the number is likely to shift with hardware or library updates.

Do not memorize a number you cannot also memorize the frame for. A decontextualised number is worse than no number.

**Associations:** Tutorials, When to memorize and recall, Marking uncertain memories, Time-sensitive memories, #prefixes-general

## Multi-person contexts

**Label:** Multi-person contexts

**Content:**
When a conversation involves multiple people, memory hygiene becomes more important — not less.

Rules:
- Always attribute — never store `"prefers short responses"` when you mean `"Alex prefers short responses"`
- Separate memories per person — never conflate preferences, opinions, or goals across people
- When people disagree — store each position separately, attributed, and associate a `Warning: conflicting views — [topic]` memory
- When someone speaks on behalf of another (`"our team prefers X"`) — flag it: `"[attributed via Sarah]"`
- Shared context (project, codebase, decision) — associate it to all relevant people but store it once, not duplicated per person

If you lose track of who said what mid-conversation — flag memories as `[attribution uncertain]` rather than guessing.

## Resolving conflicting memories

**Label:** Resolving conflicting memories

**Content:**
When two memories contradict each other, do not silently prefer one.

Steps:
1. Remember both fully — conflicts are often apparent, not real (different scope, time, or context)
2. If genuinely contradictory — check which is more recent, more specific, or better sourced
3. If resolvable — reconsolidate the weaker into the stronger, noting why
4. If irresolvable — keep both, label each with a `Warning:` memory flagging the conflict and linking both
5. Surface the conflict to the person if it affects their current task

Never silently discard the losing memory without verifying it has no remaining value.

**Associations:** When to reconsolidate, How to forget, Memory hygiene, #prefixes-general

## Marking uncertain memories

**Label:** Marking uncertain memories

**Content:**
Not all memories are equally trustworthy. Flag uncertainty at memorization time — not later.

How to mark:
- Label prefix stays the same — `Fact:`, `Claim:`, etc.
- Add `[uncertain]` at the start of content: `"[uncertain] GRDB dropped iOS 13 support in v6 — not verified"`
- Associate to a `Warning: unverified — [label]` memory for easy search

When to mark uncertain:
- Inferred rather than stated
- Recalled from memory without a source
- Plausible but not confirmed
- Sourced from a single low-confidence input

Revisit and either confirm or forget uncertain memories. An unverified memory acted on as fact is worse than no memory.

**Associations:** When to memorize and recall, Resolving conflicting memories, Memory hygiene, #prefixes-general

## Time-sensitive memories

**Label:** Time-sensitive memories

**Content:**
Some facts have a half-life. Memorize them differently.

Categories that go stale: version numbers, prices, API specs, statuses, roles, deadlines, availability.

How to handle:
- Add `[expires: reason]` at the start of content: `"[expires: next release] GRDB latest stable is 6.3.1"`
- Associate to a `Warning: may be stale — [label]` memory
- Use `Status:` prefix for anything evolving — it signals reconsolidation is expected
- At session start on a relevant topic — search for `[expires]` and verify before using

Do not treat versioned or status facts as permanent. A stale version number given confidently is a mistake.

**Associations:** Memory hygiene, When to reconsolidate, Marking uncertain memories, #prefixes-status, #prefixes-general

## What not to memorize

**Label:** What not to memorize

**Content:**
Memorizing noise degrades search quality. Default to not memorizing.

Do not memorize:
- Things easily re-derived (arithmetic, trivial lookups)
- Raw conversation transcript — extract the lesson instead
- Redundant restatements of an existing memory
- Highly context-specific facts with no future applicability
- Things the person said in passing with no clear signal of importance
- Emotional texture of a conversation (unless it reveals a preference or pattern)
- Anything marked `[uncertain]` that cannot be verified and has no consequence

When unsure — ask: "Would this change how I respond in a future conversation?" If no, skip it.

## Handling corrections

**Label:** Handling corrections

**Content:**
When the person says something you stated was wrong — treat it as a three-step process.

1. **Correct the memory** — remember the wrong memory fully, reconsolidate with the corrected fact, note the correction in content: `"corrected — previously believed X"`
2. **Damage scan** — search for any memories that depended on the wrong fact. Reconsolidate or flag each one.
3. **Root cause** — was this a bad source, bad inference, or stale fact? Memorize a `Lesson:` or `Mistake:` memory if the pattern is worth avoiding.

Do not just update the surface memory and move on. Errors propagate through associations — fix the root, then trace the branches.

**Associations:** When to reconsolidate, Resolving conflicting memories, Marking uncertain memories, Memory hygiene, Tutorials, #prefixes-general

## Failed search recovery

**Label:** Failed search recovery

**Content:**
If a first search returns nothing useful, do not conclude the memory doesn't exist. Work the ladder:

1. Try a different keyword — more specific, then more general
2. Include the prefix explicitly — `"Decision: auth"` not `"auth"`
3. Try a synonym or alternate framing — `"timeout"` vs `"expiry"` vs `"TTL"`
4. Traverse — recall something related and walk its associations
5. Remember everything — browse recent entries; the memory may be labelled differently than expected
6. Only after all five fail — conclude the memory doesn't exist, and consider whether it should be created now

A failed search is not absence of knowledge — it is often a labelling problem. If you find the memory via traversal after a failed keyword search, reconsolidate it with a better label.
